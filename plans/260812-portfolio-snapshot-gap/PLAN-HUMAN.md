# PLAN-HUMAN — 포트폴리오 스냅샷 명세 갭 해소

## PH-01. 고정형 카드 응답의 sourceArtworkId 노출 제거 여부

depends on: (없음)

명세(R39)는 "sourceArtworkId는 복제·운영 조치 확인용 내부 연결값이며, 제3자에게 원본 작품 URL을 노출하는
근거로 사용하지 않는다"고 명시하는데, 현재 `PortfolioMapper.toCardInfo()`가 고정형 카드의 `artworkId`
자리에 이 값을 그대로 내려준다. PA-03에서 `snapshotId`를 추가하는 김에 `sourceArtworkId` 노출을 없앨지
결정 필요 — 프론트가 이미 이 필드로 뭔가 하고 있다면(예: 원본 링크 조립) 응답 계약 변경이라 프론트 협의가
먼저 필요하다.

## PH-02. 스냅샷 상세에 북마크 수 등 "생성시점 고정값" 표시 여부

depends on: (없음)

명세(R39)는 스냅샷 상세에서 "북마크 수 등 부가 정보는 생성 시점 값으로 고정 노출"하라고 요구하지만, 현재
원본 작품 상세 API조차 북마크 수를 내려주지 않는다(`ArtworkInfo`에 필드 없음, `BookmarkEntryRepository`에
count 메서드 없음). Figma(`9LlQstP5i6O9G5uZbENOwq`, node `4955-2076`)의 스냅샷 상세 화면에 실제로
북마크 수가 표시되는지 확인 필요 — 표시된다면 PA-04에서 이 필드를 이번에 넣어야 한다(스냅샷은 write-once라
나중에 소급 백필이 불가능하다).

## PH-03. 라이트 ETL의 LINK_ONLY 작품 매핑 정책

depends on: (없음)

라이트 `ArtworkStatus`에 LINK_ONLY가 실존하는 값이라 마이그레이션 시 매핑 대상이다. PA-01로 새 모델(피드
OFF+포트폴리오 미포함=완전비공개)이 적용되면, 라이트에서 링크공개로 쓰이던 작품의 기존 공유 링크가
마이그레이션 후 깨진다. 이게 의도된 정책 전환인지(명세 R04가 "이전에 공유된 링크로 접근해도 열람 불가"를
근거로 제시하긴 함), 아니면 ETL 시 해당 작품을 작가 페이지 포트폴리오에 자동 편입해 접근을 보존할지 결정
필요. PA-01 코드 작업 자체를 막지는 않지만, 마이그레이션(로드맵 P6) 전에는 확정돼야 한다.

- [x] **정책 전환 인정으로 확정**(2026-08-18) — 마이그레이션 후 기존 LINK_ONLY 공유 링크는 새 2요소
      모델(피드OFF+포트폴리오 미포함=완전비공개)에 따라 접근이 막힌다. 별도 보존 로직(ETL 시 작가
      페이지 자동 편입 등)은 구현하지 않는다.

## PH-05. 업로드 API 계약 전환 방식 — 즉시 전환 vs 과도기 병행

depends on: (없음)

프론트가 이미 3값 `visibility` 계약으로 업로드 화면을 구현했는지에 따라 PA-05의 모양이 크게 갈린다. 착수
전이라면 `visibility` 필드를 아예 제거하고 `publishToFeed`(boolean) 필수로 단순화하는 게 낫고, 이미
구현돼 있다면 과도기 동안 두 계약을 상호 배타로 동시 수용해야 한다.

- [x] **즉시 전환으로 확정**(2026-08-12) — `visibility` 필드 제거, `publishToFeed`(boolean) 필수로 단순화.
      PA-05에 반영 완료

## PH-06. 구 PATCH /api/artworks/{id}/visibility 존치 여부

depends on: (없음)

PA-05가 신설하는 `PATCH .../publication`(노출위치 조합 재선언)과 기존 3값 `PATCH .../visibility`를
병행 유지할지, 아니면 이번에 구 엔드포인트를 제거할지 결정 필요.

- [x] **제거로 확정**(2026-08-12) — 구 `PATCH /visibility` 제거, `PATCH /publication`만 유지. PA-05에
      반영 완료

## PH-07. 운영 차단(모더레이션) 최소 구현 스코프 확정

- [x] **스코프 확정**(2026-08-18) — 컬럼+판정 로직만, 관리자 API·Role 체계는 로드맵 8번(다음

## PH-08. 차단된 작품을 작성자 본인에게 어떻게 보여줄지

depends on: (없음)

명세(R38)는 "선택 대상(포트폴리오 추가·복제)에서 제외한다"고만 규정하고, 작품 관리 화면 노출 여부·본인의
상세 접근 허용 여부는 공백이다. PA-02의 기본값은 "본인 열람은 허용 + 차단 안내 배지"이나, 기획 확인 필요.

- [x] **확정**(2026-08-18) — 본인 열람 허용 + 차단 안내 배지. 이미 배포된 PA-02 구현이 최종 방향.

## PH-09. 운영 차단 SQL 실행 주체·절차

depends on: (없음)

PA-02는 API를 노출하지 않으므로 실제 차단은 DB 직접 UPDATE로 이뤄진다(운영 조치 시 재색인 API 병행 호출
필요, PA-02 마지막 체크박스 참고). 누가 어떤 승인 절차로 이 SQL을 실행할지는 시스템 밖 운영 정책이라
코드 작업과 무관하지만, 사고 대응 매뉴얼에 남겨둘 필요가 있다.

- [x] **문서화로 종결**(2026-08-18) — `docs/operations/moderation-block.md`에 차단·해제 SQL, 재색인
      호출, 보관 정책까지 정리 완료. 실행 주체·승인 절차 자체는 여전히 코드 밖 운영 정책이라 팀 내에서
      별도로 정하면 된다.
