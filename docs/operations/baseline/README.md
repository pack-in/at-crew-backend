# 운영 기준선 (baseline)

이 디렉토리는 **인프라를 바꾸기 전의 수치**를 남기는 곳이다. 개선을 "빨라졌다"가 아니라
"p95가 몇 ms에서 몇 ms가 됐다"로 말하려면 바꾸기 전 값이 있어야 하는데, 이 서비스에는
관측 스택(`docs/design/observability-design.md`)은 있어도 **비교 기준값을 떠 놓은 기록이
없었다.** 첫 기록은 Elasticsearch를 EC2 #2에서 EC2 #1로 통합하기 직전에 떴다.

## 파일 규칙

| 경로 | 내용 |
|---|---|
| `YYYY-MM-DD-<상황>.md` | 그 시점의 측정 결과. **이전 파일을 덮어쓰지 않고 계속 쌓는다** |
| `../../../scripts/baseline/collect-host.sh` | EC2 #1에서 실행하는 A·B·C군 수집기 |
| `../../../scripts/baseline/load-test.js` | k6 부하 시나리오(읽기 전용) |
| `../../../scripts/baseline/restore-drill.sh` | 로컬 복구 훈련. 단계별 소요시간 출력 |

파일명에 상황을 넣는 이유는 날짜만으로는 나중에 무엇과 무엇을 비교해야 하는지 알 수 없기
때문이다(`2026-09-02-pre-es-consolidation.md` ↔ `-post-es-consolidation.md`처럼 짝을 이룬다).

## 측정 항목

| 군 | 내용 | 언제 다시 재나 |
|---|---|---|
| **A. 구성** | 인스턴스 타입·메모리·디스크, 컨테이너 목록과 메모리 상한, JVM 힙 / `innodb_buffer_pool_size` / ES 힙, **Elasticsearch 배치(분리/통합)** | 인스턴스나 컨테이너 구성이 바뀔 때 |
| **B. 성능** | 정상 상태 CPU·메모리·스왑·디스크IO·로드애버리지(24h 평균/p95/최대), 컨테이너별 메모리 실사용, API p95/p99·5xx, 한계 처리량, **CPU 크레딧 수지**, 기동~헬스체크 UP 시간, 엣지 구간 오버헤드 | 구성 변경 전후, 그리고 분기 1회 |
| **C. 데이터** | 테이블별 행수·크기, DB 총 크기, 덤프 크기·소요시간, 커넥션 풀, 슬로우 쿼리, ES 인덱스별 문서수·크기 | 데이터가 한 자릿수 배 이상 늘 때 |
| **D. 운영** | RTO 실측·복원 정합성, RPO, 배포 소요시간·무응답 구간, 롤백 소요시간, 업타임·MTTR, 월 비용 | 반기 1회, 그리고 백업·배포 절차를 바꿀 때 |

## 값을 적는 방법

**평균만 적지 않는다.** 이 서비스의 어제자 CPU는 평균 1.95%인데 p95는 1.32%다 — 평균이 p95보다
큰 건 하루에 몇 분 100%까지 튀는 구간(백업·이미지 정리)이 평균을 끌어올리기 때문이고, 평균만
적었으면 이 사실이 사라진다. **평균·p95·최대를 같이 적는다.**

**측정 조건을 같이 적는다.** 시각(UTC), 부하 수준, 그때 동시에 돌던 작업. 조건이 빠진 수치는
다음 측정과 비교할 수 없다.

**못 잰 것은 빈칸이 아니라 `측정 불가`로 적고 이유를 쓴다.** 수집 스크립트도 같은 규칙으로
`측정 실패`를 출력한다 — "0이었다"와 "안 쟀다"를 구분하지 못하면 다음 사람이 잘못 읽는다.

## 수행 시 주의

**버스터블 인스턴스에서는 크레딧 수지를 같이 본다.** `t4g` 계열은 CPU 크레딧이 남아 있는
동안에만 전력을 낸다. 부하 테스트로 나오는 처리량은 **버스트 성능**이고, 크레딧이 고갈되면
vCPU의 20%로 제한된다. 그래서 구성 변경의 영향은 순간 성능보다 `CPUCreditBalance`의 시간당
순증감에서 먼저 드러난다 — 측정 전후로 이 값을 함께 기록한다.

**부하 테스트가 서비스를 멈출 수 있다.** 앱·MariaDB·(통합 후)Elasticsearch가 한 인스턴스의
메모리를 나눠 쓰고 **스왑이 없다.** 메모리가 모자라면 OOM 킬러가 컨테이너를 죽인다. 백업이 성공한
직후에, 읽기 전용 엔드포인트만, 중단 조건을 미리 정해 놓고 수행한다.

**부하는 로컬에서 만들고 서버에서는 수집만 한다.** 서버에 k6를 설치하면 부하 생성기 자신이
측정 대상의 CPU와 메모리를 먹어서 값이 오염된다.

**서버에 스크립트 파일을 두지 않는다.** `ssh ... 'bash -s' < scripts/baseline/collect-host.sh`로
표준입력에 흘려 넣으면 서버에 아무것도 남지 않고, 레포의 스크립트가 항상 유일한 정본이 된다.

**복구 훈련은 실서버에서 하지 않는다.** 로컬 컨테이너에 R2 덤프를 복원하는 방식으로 한다.
이렇게 잰 RTO는 "데이터 복원 시간"이고, 실제 장애 때의 RTO에는 인스턴스 재생성 시간이 더해진다.

**출력에 식별자를 넣지 않는다.** 이 저장소는 공개다 — 인스턴스 ID·탄력적 IP·프라이빗 IP·
VPC/보안 그룹/AMI ID는 결과 문서에도 스크립트 출력에도 적지 않는다(`deploy/README.md`와 같은
원칙). 수집 스크립트는 Elasticsearch 주소도 찍지 않고 "분리/통합"이라는 배치 판정만 낸다.

## 실행

```bash
# A·B·C군 — EC2 #1에서 수집, 결과는 로컬에 받는다
ssh -i ~/.ssh/<키페어>.pem ec2-user@<EC2 #1> 'bash -s' < scripts/baseline/collect-host.sh \
  > docs/operations/baseline/$(date -u +%F)-<상황>.md

# D군 RTO — 로컬에서만
./scripts/baseline/restore-drill.sh

# B군 한계 처리량 — 로컬에서 부하 생성. 아래 주의사항을 먼저 읽을 것
k6 run scripts/baseline/load-test.js
```
