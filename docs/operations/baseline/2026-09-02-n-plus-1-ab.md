# N+1 개선 전후 A/B 측정 (2026-09-02)

**대상**: 이슈 #112 / PR #113 — `Artwork`의 EAGER 컬렉션 8개에 `@BatchSize(size = 100)` 적용

**측정 방법**: 임시 인스턴스 1대에서 **jar만 바꿔가며** 측정했다. MariaDB·Elasticsearch·시드
데이터·JVM 베이스 이미지가 모두 동일하게 유지되므로, 두 결과의 차이는 코드 변경뿐이다.

| 항목 | 값 |
|---|---|
| 인스턴스 | `t4g.medium`, 2 vCPU, 3,830 MB — 프로덕션과 동일 사양 (측정 후 종료) |
| 구성 | `app`(마운트한 jar) + `mariadb` + `elasticsearch` 한 인스턴스 |
| 데이터 | 회원 5,000 / 작품 100,000 / 이미지 100,000 / 구인글 5,000, DB 174 MB |
| Elasticsearch | 작품 100,000건 색인 (재색인 321초) |
| 부하 | 로컬 k6 → SSH 터널 → 오리진 앱 직접, 읽기 전용 GET 6종 |
| 워밍업 | **각 측정 전 동일하게 480요청.** 이걸 빼면 결과가 뒤집힌다(아래 §4 참고) |

<br>

## 1. 요청당 SQL 쿼리 수 — 명확한 개선

`SHOW GLOBAL STATUS LIKE 'Com_select'` 전후 차이, 요청 5건 평균.

| 엔드포인트 | BEFORE | AFTER | 변화 |
|---|---|---|---|
| `GET /api/community/artworks?size=20` | **210건** | **50건** | **-76% (4.2배 감소)** |
| `GET /api/recruit/job-postings?size=20` | 44건 | 44건 | 변화 없음(이미 `@BatchSize` 적용됨) |

리포지토리 계층 단위 테스트에서는 항목 20개 조회 시 161회 → 20회 이하로 갈린다
(`ArtworkCollectionFetchTest`). API 경로의 50회에는 작가 조회 등 컬렉션 밖의 쿼리가 포함된다.

<br>

## 2. 처리량 — 개선되지만 폭은 제한적이다

| 경과 | BEFORE RPS / p50 | AFTER RPS / p50 |
|---|---|---|
| 60s | 14.1 / 39.3 ms | 12.1 / 17.4 ms |
| 75s | 17.5 / 36.5 ms | 15.5 / 21.2 ms |
| 90s | 23.5 / 91.3 ms | 19.7 / 38.0 ms |
| **105s** | **23.1 / 2,112.0 ms** | **24.2 / 111.0 ms** |
| 120s | 8.9 / 2,726.7 ms | 27.5 / 2,279.0 ms |

**꺾이는 지점이 약 23 RPS에서 약 27 RPS로 이동했다(+약 17%).** 더 눈에 띄는 것은 같은 부하에서의
지연이다 — **23~24 RPS 구간에서 p50이 2,112 ms에서 111 ms로 19배 낮다.** BEFORE는 이 지점에서
이미 무너져 있고 AFTER는 아직 정상 범위다.

엔드포인트별 p95도 전반적으로 내려갔다(작품 피드 4,976 → 3,730 ms, 작가 목록 3,113 → 1,529 ms).

**다만 처리량 자체의 개선은 17% 수준이다.** 쿼리 수를 4.2배 줄였는데 처리량이 그만큼 오르지
않는 이유는 §3에 있다.

<br>

## 3. 병목은 여전히 커넥션 풀과 CPU다

| 자원 | AFTER 포화 시점 | 판정 |
|---|---|---|
| **HikariCP 커넥션** | **10 / 최대 10** | **여전히 소진** |
| CPU | 최대 88.3% | 높음 |
| 로드 애버리지 | 5.93 (vCPU 2개) | 높음 |
| 메모리 available | 1,307 MB | 여유 |

쿼리 수를 줄여도 **DB가 읽어야 하는 행의 총량은 같다.** 배치 페치는 왕복 횟수를 줄이는 것이지
작업량을 줄이는 것이 아니다. 같은 호스트의 소켓 통신이라 왕복 비용이 작아서(수십 μs), 160회를
줄여 아낀 시간이 p50 수백 ms 앞에서는 지배적이지 않다.

### 3.1. `innodb_buffer_pool_size`를 올려도 달라지지 않았다 — 음성 결과

DB가 174 MB인데 `innodb_buffer_pool_size`가 기본값 128 MB라 "작업 집합이 안 들어간다"고 보고
**1 GB로 올려 같은 측정을 반복했다.**

| 경과 | AFTER (풀 128 MB) | AFTER (풀 1 GB) |
|---|---|---|
| 90s | 19.7 RPS / 38.0 ms | 19.1 RPS / 28.3 ms |
| 105s | 24.2 RPS / 111.0 ms | 25.0 RPS / 247.7 ms |
| 120s | 27.5 RPS / 2,279.0 ms | 22.5 RPS / 2,292.8 ms |

**차이가 없다.** 버퍼풀은 이 워크로드의 병목이 아니다 — OS 페이지 캐시가 이미 파일을 들고 있고,
비용은 디스크 IO가 아니라 쿼리 실행(CPU)에 있다. **이 항목을 튜닝 대상에서 제외한다.**

<br>

## 4. 측정 방법에서 배운 것 — 워밍업 없이는 결론이 뒤집힌다

처음에는 워밍업 없이 BEFORE → AFTER 순으로 측정했고, **AFTER가 더 나쁘게 나왔다**(평균 13.2 →
11.4 RPS). AFTER가 컨테이너 재생성 직후라 JIT가 덥혀지지 않은 상태였기 때문이다.

각 측정 전에 동일한 480요청 워밍업을 넣자 결과가 뒤집혀 AFTER가 일관되게 우세해졌다.

**평균 RPS로 비교하지 않는다.** 이 시나리오는 임계 초과 시 중단되므로 중단 시점이 다르면 평균이
달라진다. 워밍업 후 평균은 BEFORE 13.8, AFTER 14.4로 4% 차이지만, 구간별 곡선을 보면
23~24 RPS에서 p50이 19배 갈린다. **비교는 반드시 구간별 곡선으로 한다.**
