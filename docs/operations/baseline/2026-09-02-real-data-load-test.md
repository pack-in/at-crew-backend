# 실데이터 규모 부하 테스트 (2026-09-02)

**목적**: `2026-09-02-pre-es-consolidation.md`의 한계 처리량(약 950 RPS)은 DB 실데이터 85행
상태에서 나온 값이라 **상한일 뿐 서비스 능력이 아니었다.** 실사용 규모의 데이터를 넣고 다시 재서

## 1. 결론 — 데이터가 없으면 측정도 없다

| 데이터 규모 | DB 크기 | 한계 처리량 | 빈 DB 대비 |
|---|---|---|---|
| 85행 (통합 전 프로덕션) | 2.3 MB | **약 950~1,030 RPS** | 기준 |
| 작품 10,000건 | 17.5 MB (버퍼풀 안) | **약 70 RPS** | **1/14** |
| 작품 100,000건 | 174 MB (버퍼풀 초과) | **약 15 RPS** | **1/65** |

**빈 DB에서 잰 950 RPS는 실사용 규모에서 15 RPS였다.** 65배 차이다. 이 수치를 그대로 인용했다면
용량 산정이 두 자릿수 배로 틀어졌을 것이다.

`innodb_buffer_pool_size`는 128 MB다. 10,000건(17.5 MB)은 전부 메모리에 올라가고,
100,000건(174 MB, 그중 `artworks` 테이블만 125 MB)은 넘친다. 두 구간을 모두 측정한 이유다.

## 3. 병목 — CPU가 아니라 커넥션 풀과 N+1이다

| 자원 | 포화 시점 | 판정 |
|---|---|---|
| **HikariCP 커넥션** | **10 / 최대 10** (완전 소진) | **주 병목** |
| 로드 애버리지 | 7.02 (vCPU 2개) | 높으나 커넥션 대기의 결과 |
| CPU | 최대 87.3% | 포화 아님 |
| 메모리 available | 1,564 → 1,402 MB (162 MB 감소) | 병목 아님 |
| JVM 힙 | 최대 277 MB / 958 MB | 병목 아님 |

통합 전 빈 DB 측정에서는 CPU가 97.99%까지 차서 CPU를 주 병목으로 봤는데, **실데이터에서는
CPU가 87%에 머무는 동안 커넥션 풀이 먼저 마른다.** 원인은 쿼리 수다.

### 3.1. 요청당 SQL 쿼리 수 (`Com_select` 실측)

| 엔드포인트 | 요청당 SELECT | 비고 |
|---|---|---|
| `/api/community/artworks?size=20` | **189건** | 항목 20개에 대해 작품당 약 9.5회 |
| `/api/recruit/job-postings?size=20` | **44건** | 항목당 약 2.2회 |
| `/api/community/authors?size=20` | 1건 | 정상 |
| `/api/search?q=…&size=20` | **0건** | 전부 Elasticsearch에서 처리 |

**커뮤니티 작품 피드는 한 번 호출에 SELECT를 189번 던진다.** 커넥션 10개짜리 풀에서 이 요청이
초당 15건만 들어와도 초당 약 2,800회의 쿼리가 되고, 풀이 마르는 것이 당연하다.

`ArtworkServiceImpl.toSummaryPage`에는 이미 `// 작가 정보 일괄 조회 (N+1 완화 — 향후 batch API
추가 예정)`라는 주석이 있다. **완화가 아직 안 됐고, 이 측정이 그 비용을 처음으로 수치화했다.**

## 4. 엔드포인트별 — 검색 모듈의 존재 이유

작품 100,000건, 포화 직전 구간 기준.

| 엔드포인트 | 백엔드 | p50(ms) | p95(ms) |
|---|---|---|---|
| `/api/community/artworks` | MariaDB | **931.0** | 3,933.5 |
| `/api/recruit/job-postings` | MariaDB | 94.9 | 1,873.9 |
| `/api/community/banners` | MariaDB | 27.8 | 1,801.6 |
| `/api/community/authors` | MariaDB | 26.6 | 1,816.9 |
| `/api/billing/catalog` | 앱 내부 | 26.6 | 1,607.0 |
| **`/api/search`** | **Elasticsearch** | **104.7** | **224.8** |

**부하가 걸린 상태에서 Elasticsearch 검색이 MariaDB 작품 피드보다 p50 기준 9배, p95 기준
17배 빠르다.** 검색만 SQL을 한 번도 던지지 않아 커넥션 풀 경합에서 빠져 있기 때문이다.

데이터가 10배(10,000 → 100,000)로 늘 때 검색 p50은 58 ms → 105 ms로 1.8배만 늘었다.
같은 구간에서 작품 피드는 458 ms → 931 ms다.

**이슈 #76에 대한 함의**: 통합 전 측정에서는 "검색이 EC2 #2의 놀고 있는 CPU를 쓰고 있어
통합하면 그 부담이 넘어온다"고 봤다. 실데이터로 재보니 그림이 다르다 — **검색은 애초에
DB 커넥션을 쓰지 않아서 빠른 것이고, 통합 후 한 인스턴스에서도 여전히 가장 빠른 엔드포인트다.**
통합의 실제 대가는 CPU 경합보다 작다.

## 6. 한계

**부하 경로에 Cloudflare와 nginx가 빠져 있다.** SSH 터널로 오리진 앱에 직접 보냈으므로 위
수치는 애플리케이션과 MariaDB의 처리 능력이지 사용자 체감값이 아니다.

**더미 데이터의 분포가 실사용과 다르다.** 작가 1명당 작품 20건이 고르게 분포하고, 설명 길이도
평균 558바이트로 균일하다. 실제로는 인기 작가에 쏠리고 길이도 들쭉날쭉하다. 캐시 적중률이
실제와 다를 수 있다.

**북마크·조회수 갱신 같은 쓰기 부하가 없다.** 읽기 전용 GET만 측정했다. 쓰기가 섞이면
커넥션 풀 경합은 더 심해진다.

**단발 측정이다.** 각 규모에서 1회씩만 돌렸다. 추세를 말하기에는 충분하지만 오차 범위는 모른다.

## 7. 다음에 확인할 것

1. **N+1 제거 후 재측정.** `ArtworkServiceImpl`의 작가 일괄 조회를 batch로 바꾸면 요청당
   189 SELECT가 얼마나 줄고 처리량이 얼마나 오르는지. 이 측정이 그 개선의 기준선이 된다.
2. **HikariCP 풀 크기 조정.** 현재 10이다. 늘리면 병목이 DB로 옮겨갈 뿐인지, 실제로 처리량이
   오르는지. N+1을 먼저 고치는 편이 순서상 맞다.
3. `innodb_buffer_pool_size` 128 MB는 기본값이다. 인스턴스 메모리 3,830 MB 대비 과소하다.
