더 커지고, 신규 모듈을 Mongo 기준으로 설계했다가 다시 JPA로 다시 짜는 이중 작업이 발생함. 지금 마이그레이션을
끝내두면 이후 모든 신규 모듈은 처음부터 MariaDB/JPA로 한 번에 설계 가능.

## 0. MongoDB → MariaDB 마이그레이션

설계는 이미 완료된 상태(`docs/design/mariadb-migration-design.md`, 상태: 설계안 → 구현 착수).
ID 전략(String 유지, VARCHAR(36), 신규 레코드는 UUIDv7), 스키마 정규화, 원자 연산 재설계, Flyway,
Spring Modulith JDBC 이벤트 레지스트리 교체, ETL·컷오버 계획까지 포함. API 계약(요청/응답 DTO)은
변경하지 않는 것이 원칙.

**이 로드맵과의 관계:** 1~6번 항목(신규 모듈)은 전부 이 마이그레이션 완료 이후 착수한다. 마이그레이션
자체는 기존 4개 모듈(auth/member/artwork/community)의 영속성 계층 전환이 스코프이며 신규 기능 추가는 아님.

## 1. 본인/기업 인증(verification) 시스템

**Why 최우선으로 승격했는가:** artwork(성인물 게이팅) → community(성인물 게이팅) → recruit(업로드 게이팅), 기업 프로필(구인글 업로드 게이팅) 순으로 **같은 블로커에 세 번째** 부딪힘. 지금까지는 매번 "인증 필드 없음 → 클라이언트 필터로 임시 처리"로 미뤄왔는데(artwork/community 모듈 회고 참고), 이번엔 제대로 설계하기로 결정.

**필요한 것:**
- `Member`에 인증 상태 필드 추가 (성인 인증 여부·완료일·재인증 만료일, 기업 인증 상태(검토중/완료/반려) — 별개 개념으로 분리)
- 기존에 미뤄뒀던 게이팅 로직 소급 적용: artwork/community의 성인물 게이팅(썸네일 blur, 업로드 차단), recruit 성인 대상 공고 지원 게이팅

**방식 확정(2026-07-31, 기획서 설정-R07·R08 기준):**
- **본인 인증(성인 인증)**: PASS 인증 모듈 연동(외부 서비스). 유효기간 1년, 만료 1개월 전부터 세션당 1회 재인증 유도 모달. 만 19세 미만은 인증 완료해도 성인 콘텐츠 이용 불가로 별도 처리.
- **기업 인증**: 외부 API 연동 없는 **수동 심사**. 기업이 사업자등록증을 운영 이메일로 전송 → 운영자가 육안 확인 후 검토중/인증완료/반려 3상태를 수동 전환. 시스템은 상태 필드·안내 모달만 제공하면 되고 진위 확인 로직은 불필요.
- 재가입 제한(로그인-R12, 탈퇴 10일)·성인 콘텐츠 표시 설정(설정-R10, 표시 OFF/ON+미인증 blur/ON+인증 원본) 등 인증과 맞물리는 정책은 `docs/AT-CREW_서비스기획서_전체_20260728.xlsx` 정책 시트(로그인-R12, 설정-R10)에 상세.

**Figma/기획서 근거:**

## 2. recruit 모듈

**Why 다음 순서인가:** community 모듈 구현 시점에 이미 laiteu 필드 조사가 끝나 있어(`docs/design/community-module-design.md` §9, [[project_community_module]] 메모) 설계 착수 난이도가 낮음. community의 `RecruitFeedPort`/`NoopRecruitFeedPort` 스텁을 실제 구현으로 대체하는 자연스러운 다음 단계.

**스코프:**
- 구인글(JobPosting)/팀원모집글(TeamPosting)/구직글(JobSeekingPost) CRUD — **구현 진행 중**(워크트리 `recruit-module`, JobPosting/TeamPosting 위주, JobSeekingPost·Application은 미착수)
- 지원(Application) 플로우, 지원자 관리(전체 지원자/최종 합격 이동, 이력서 다운로드)
- 마감된 공고 정책(작성일+2개월, 삭제 불가·수정만 가능)
- **끌어올리기(boost)** — 구인글·팀원모집글 각각 별도 유료 단건상품, 적용 시 48시간 상단고정, 마지막 적용 후 48시간 재적용 쿨다운. **(2026-07-31 스코프 복원, 아래 참고)**
- **관심 작가** — 기업 전용, 작가 프로필 좋아요(♡) 저장/해제 + 최근 본 작가 자동 기록, 구인구직 > 작가 관리 탭에서 검색·정렬 조회. **(2026-07-31 스코프 복원, 아래 참고)**

**2026-07-31 스코프 정정 — 끌어올리기·관심 작가 재편입:** 설계 당시(`recruit-module-design.md` §9)에는 laiteu에 끌어올리기 구현이 없고 관심 작가는 "로드맵 범위 밖"이라 판단해 Phase 2로 미뤘으나, 정식 기획서(`docs/AT-CREW_서비스기획서_전체_20260728.xlsx`) 대조 결과 **둘 다 P0 요구사항**(REQ-015 구인구직, REQ-017 구인구직 관리)으로 명시돼 있음이 확인됨. 기획서가 정본이므로 이번 스코프에 포함한다. 끌어올리기는 Polar 결제 모듈이 아직 없으므로 구매 검증 없이 API 자체는 먼저 구현하고(다른 모듈 게이팅 스텁과 동일 패턴), 실 결제 연동은 5번(결제) 모듈 완성 후 연결하는 TODO로 남긴다.

**laiteu 대비 참고사항 (이미 조사 완료, [[project_community_module]] 메모에 상세):**
- `JobPosting`: 회사정보/급여체계(연봉제·MG+RS)/이력서 필수여부/부스트(48시간)/PENDING 승인 절차
- `TeamPosting`: 승인 절차 없음(즉시 게시), 참여비용/수익배분, 부스트 없음 — **단, 앳크루 기획서는 팀원모집글에도 끌어올리기를 요구**(laiteu와 다른 지점, 위 참고)
- `JobSeekingPost`: laiteu에 대응 없는 신규 엔티티(Figma에서만 확인) — 작화스타일/선호피드백방식/작업스타일/희망단가
- 기술부채 주의: laiteu `JobApplication.artworkPublicId`가 실제로는 jobPostingPublicId를 가리키는 오명명 필드, TeamPosting 지원자 조회에 소유권 검증 누락 이력 있음 — 앳크루에서는 처음부터 바르게 설계할 것
- `WorkLocationType` enum이 JobPosting/TeamPosting에서 이름 같고 값 다르게 중복 정의돼 있었음 → 앳크루에서는 `JobWorkLocationType`/`TeamWorkLocationType`으로 이름 분리 필요
- laiteu는 커뮤니티 쿼리 성능 이슈(p95 7.3s) 이력 있음 — artwork 모듈처럼 처음부터 커서 페이지네이션+복합 인덱스로 설계

**Figma/기획서 근거:** `UI개편_구인구직(창작자/기업 둘 다)` (node 5154:41764), `UI개편_구인글세부페이지` (5154:41397), `UI개편_팀원모집글세부페이지` (5154:41765). 기획서 REQ-015~017, 정책 업로드-R10·구인구직-R02·구인글 상세 페이지-R05, 기능명세 구인구직-R04·R05·구인글 상세 페이지-R02·R06·R09.

**2026-07-31 구현 완료(main 병합, PR #34, 이슈 #33)**: JobPosting/TeamPosting/JobSeekingPost CRUD, Application 지원·지원자 관리, 끌어올리기, 관심 작가, `RecruitService` 공개 API 이관까지 전부 병합됨.

**Figma 근거:** `UI개편_마이페이지_기업` (5154:41398), `UI개편_마이페이지_기업_수정페이지` (5244:25813)

## 5. 결제/구독(요금제) — 설정

**Why 뒤로 미뤘는가:** 스코프가 예상보다 큼 — PG 연동, 정기결제, 환불 정책까지 포함된 실제 결제 시스템. "기업 인증 후 요금제 안내 로직"으로 설계돼 있어 3번(기업 프로필, 완료됨) 완료가 선행조건이었음 — 이제 착수 가능.

**PG 확정(2026-07-31): Polar** — 결제·구독 관리·환불·결제수단 변경은 전부 Polar에서 처리하고, 앳크루 백엔드는 (1) 상품 노출 (2) Polar Checkout 진입 (3) 웹훅 수신 후 권한 반영만 담당한다. 자체 결제 UI·PG 직접 연동 없음.

**상품 구조 (기획서 요금제-R02~R06 기준):**
- 구독형: 스타터(무료, 전 가입자 기본)/프로 월간(7,500원, 정가 15,000원)/프로 연간(75,000원, 정가 150,000원). 스타터↔프로 전환·월간↔연간 변경.
- 단건 게시 상품: 팀원 모집글 업로드 권한(50,000원, 끌어올리기 1회 포함)/끌어올리기(10,000원). 구매 시 보유 개수 +1, 게시 성공 시에만 차감(실패 시 미차감), 만료 없음.
- 정기 결제 실패: Polar 웹훅 기준 판별, 유예 없이 즉시 스타터 전환+이메일 알림, 재결제 성공 시 웹훅 기준 복원.
- 탈퇴 시 Polar Delete Customer API로 활성 구독 즉시 취소(잔여 기간 환불 여부는 Polar 정책 확인 필요 — 미확정).

**스코프:**
- 요금제 페이지(비로그인, 스타터/프로/단건 카드), 설정 > 요금제 및 결제 탭(로그인, 프로+단건 카드만)
- Polar Checkout 연동, 웹훅 핸들러(결제 성공/실패/구독 변경/취소)
- 플랜 다운그레이드 시 기존 산출물 유지 정책(REQ-020 — 공유 링크·포트폴리오는 유지, 신규 생성만 제한)
- 정기 결제 실패 이메일 알림 — **이메일 발송 인프라 필요**(현재 없음, 비밀번호 재설정 메일 발송 로직 재사용 가능 여부 확인 필요)

**Figma/기획서 근거:** `UI개편_설정` (5154:41400) 내 "요금제 및 결제 Tab bar 화면" 섹션(6230:47908). 기획서 REQ-020·021, 정책 설정-R03·R11·요금제-R01·R02·R06, 기능명세 설정-R01~R03·요금제페이지-R01·요금제-R03~R05.

## 7. 다국어(i18n) UI 로컬라이제이션 — 신규(2026-07-31)

**Why 신규 항목인가:** 기존 로드맵 어디에도 명시적으로 없었으나, 기획서 REQ-019(다국어)가 P1 우선순위로 서비스 전반에 걸쳐 있고 `global-timezone-strategy.md` §5.1에서도 별도 과제로 플래그돼 있었음. 범위가 커서 단일 모듈이 아닌 크로스커팅 인프라로 별도 항목화.

**스코프 (정책 로그인-R16, 설정-R14, 데이터구조-R06 기준):**
- 서비스 UI 4개 언어(한국어/일본어/중국어/영어) 현지화 — `MessageSource`/`Accept-Language` 기반 로케일 처리 현재 전무(에러·검증 메시지 100% 하드코딩 한국어, `global-timezone-strategy.md` §5.1 참고)
- `Member.primaryLanguage`(주 사용 언어, 가입 시 필수 선택·가입 후 변경 불가) 신규 필드
- 언어 세그먼트: 주 사용 언어가 다른 사용자 간 계정·게시글 기본 비노출(홈 피드·검색·마이페이지·구인글 목록, 딥링크는 예외) — `Member.postLanguages`(게시물 언어 선택, 복수, 설정에서 확장 가능) 신규 필드
- 검색 인덱스에 언어 필터 반영 — search 모듈(4번, 완료됨) 확장 필요
- 자동 번역은 서비스 UI 현지화에만 적용, 사용자 생성 콘텐츠는 번역하지 않음

**선행 검토:** `ActiveRegion` enum이 현재 한국 행정구역 전용 — 글로벌 회원 표현을 위한 재설계 필요(`global-timezone-strategy.md` §5.2, 이번 스코프에 포함할지 별도 결정 필요).

## 8. 관리자/모더레이션 콘솔 — 신규(2026-07-31)

**Why 신규 항목인가:** recruit(`구인글 PENDING 승인/반려`), 홈 피드(`신고 누적 콘텐츠 검토`) 등 여러 모듈에서 "관리자 권한 체계 없음"을 공통으로 스텁 처리해왔는데, 기획서에서 정식 요구사항으로 두 번 이상 반복 등장해 더 이상 개별 모듈 TODO로 미루기 어려움.

**스코프 (정책 홈-R15, 기능명세 설정 인접 항목 기준):**
- 관리자 역할(Role) 체계 — member 모듈에 아직 없음
- 콘텐츠 노출 상태 5종 관리: 정상/작성자 비공개/작성자 삭제/신고 누적 검토중/운영자 숨김. 신고 3회 누적 시 자동으로 "신고 누적 검토중" 전환(임시 숨김), 운영자가 정상 복원 또는 운영자 숨김으로 확정
- 구인글 PENDING 승인/반려 처리(recruit 모듈, 현재 인증 없이 접근 가능한 스텁 상태)
- 기업 인증(1번) 검토중/완료/반려 수동 처리 화면
- **초기 버전에는 사용자 신고 접수 UI(버튼·사유 선택) 자체는 포함하지 않음** — 상태 관리·자동 전환·운영자 처리만 우선

**Figma/기획서 근거:** 기획서 정책 홈-R15(신고 3회 누적 처리), 정책 구인구직-R02·설정-R08(기업 인증 3상태).

## 9. 소셜 공유 메타(OG 카드) — 신규(2026-07-31)

**Why 신규 항목인가:** 작품 상세·구인글 상세·팀원모집글 상세·작가 프로필·기업 프로필·포트폴리오 등 공유 가능한 화면 전부에서 OG 카드(썸네일·제목·설명) 요구사항이 반복 등장하는데 지금까지 어떤 설계 문서에도 반영돼 있지 않았음.

**스코프:** 각 상세 페이지에 OG 메타 태그(`og:image`/`og:title`/`og:description`) 서버 렌더링 또는 메타 태그 엔드포인트 제공. 성인물(R18/G18) 콘텐츠는 썸네일을 서비스 기본 이미지로 대체. 삭제·비공개·정지 케이스는 각 모듈의 접근 제한 처리와 동일 규칙 적용.

**Figma/기획서 근거:** 기능명세 작품 상세 페이지-R08, 마이페이지_작가-R45, 마이페이지_작가-R44, 마이페이지_기업-R10, 구인글 상세 페이지-R07, 팀원 모집글 상세 페이지-R01.
