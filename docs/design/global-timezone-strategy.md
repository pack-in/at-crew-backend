| 항목 | 결정 |
|------|------|
| 저장 계층 | 변경 없음 — 이미 전 도메인이 `Instant`(UTC) 사용 중. **가장 큰 리스크가 이미 해결되어 있음** |

## 1. 현재 상태 진단 (as-is)

Explore 조사 결과 기준 (2026-07-15):

| 항목 | 현황 | 평가 |
|------|------|------|
| 도메인 시간 필드 | 전 21개 파일이 `java.time.Instant` 사용, `LocalDateTime`/`ZonedDateTime` 0건 | ✅ 양호 — UTC 저장이 이미 관행화되어 있음 |
| DB | MongoDB, `Instant` → BSON UTC Date로 저장 | ✅ 저장 계층은 timezone-safe |
| API 직렬화 | `application.yml:15` `spring.jackson.time-zone: Asia/Seoul` | ⚠️ 설정 자체가 오해 소지 — Instant는 기본적으로 ISO-8601 UTC(`Z`)로 직렬화되지만, 이 설정이 남아있으면 향후 `OffsetDateTime` 도입이나 Jackson 기능 플래그 변경 시 KST가 새어나갈 위험 |
| 컨테이너/JVM 기본 시간대 | Dockerfile 없음, `docker-compose.yml`/CI에 `TZ` 환경변수 없음 | ⚠️ 암묵적 — 배포 환경(OS/컨테이너 베이스 이미지)의 기본값에 의존 |
| 로깅 | `logging.pattern.level`만 커스텀, 타임스탬프 포맷은 Spring Boot 기본값 | ⚠️ 명시적 시간대 없음 |
| 회원 프로필 | `Member`에 country/region/locale/timezone 필드 전무. `ActiveRegion`은 서울·경기·대전·대구·광주·부산 등 **한국 행정구역 전용 enum** | ❌ 글로벌 회원을 표현할 수 없음 |
| 스케줄링 | `ImageRetryScheduler`, `OrphanImageCleanupScheduler` 모두 `fixedDelay` (cron 아님) | ✅ 시간대 영향 없음 |
| i18n | `MessageSource`/`LocaleResolver`/`messages.properties` 전무, 에러 메시지·검증 메시지 100% 하드코딩 한국어 | ❌ 별도 과제(§5.1) |

**결론**: 걱정했던 것보다 기반은 좋다. `Instant` 전면 채택 덕분에 "저장된 시간이 실제로 잘못됐다"는 최악의 시나리오는 이미 피해있다. 남은 작업은 (1) 암묵적으로 남아있는 KST 의존을 명시적 UTC로 교체, (2) 회원별 시간대를 표현·활용할 수 있는 구조 추가, (3) 향후 모듈(recruit 등)에서 같은 원칙을 강제할 가이드라인 확립이다.

## 2. 핵심 원칙

1. **저장·연산은 항상 UTC, 표시만 로컬** — 서버는 어떤 계층에서도 "지금이 몇 시인지"를 특정 지역 기준으로 판단하지 않는다. `Instant.now()`를 그대로 유지하고, 로컬 시간이 필요한 순간(알림 발송 시각 등)에만 명시적으로 회원의 `timezone`을 참조해 변환한다.
2. **시간대는 오프셋이 아니라 IANA tz ID로 저장** — `+09:00` 같은 고정 오프셋은 미국·유럽처럼 서머타임(DST)을 쓰는 지역에서 연 2회 어긋난다. 일본·중국은 DST가 없고 미국·유럽은 있어 이 차이가 실제로 발생한다. `ZoneId.of("America/New_York")`처럼 ID로 저장해야 `ZonedDateTime` 변환 시 DST가 자동 반영된다.
3. **날짜만 있는 값(생일, 마감일 등)은 "누구의 하루인가"를 항상 명시** — `LocalDate` 자체는 시간대가 없으므로, 이를 특정 시각의 경계로 바꾸는 순간(예: "마감일 23:59:59") 반드시 기준 시간대를 코드에 명시해야 한다. 암묵적으로 서버 로컬을 쓰면 리전마다 마감 시각이 달라지는 버그가 생긴다.
4. **클라이언트가 로컬라이즈, 서버는 원본(UTC)만 제공** — 날짜 포맷(`MM/DD/YYYY` vs `DD.MM.YYYY` vs `YYYY年MM月DD日`)은 서버가 문자열로 가공해 내려주지 않는다. ISO-8601 UTC 인스턴트를 내려주면 클라이언트(웹/앱)가 기기 로케일로 렌더링한다. 서버가 미리 포맷하면 다국어 클라이언트마다 대응이 늘어난다.

## 3. 변경 사항

### 3.1 컨테이너/JVM 기본 시간대를 UTC로 명시 고정

**결정**: `docker-compose.yml`, 배포 매니페스트, CI 워크플로우에 `TZ=UTC` 환경변수 명시. JVM 옵션으로도 `-Duser.timezone=UTC` 추가(이중 안전장치).

**근거**: 현재는 설정이 없어 배포 환경의 OS 기본 시간대에 암묵적으로 의존한다. `Instant.now()`는 시간대 무관이라 당장 문제는 없지만, 향후 실수로 `LocalDate.now()`/`LocalDateTime.now()`를 쓰는 코드가 추가되면(예: "오늘 가입한 회원 수" 같은 집계) 배포 환경마다 결과가 달라지는 재현 불가능한 버그가 생긴다. 명시적 UTC 고정은 이 클래스의 버그를 원천 차단한다.

**트레이드오프**: 없음 — 순수하게 안전장치 추가.

### 3.2 Jackson 직렬화 정책: KST → UTC

**결정**: `application.yml`의 `spring.jackson.time-zone: Asia/Seoul`을 `UTC`로 변경(또는 라인 자체를 제거해 Jackson 기본값인 UTC에 위임).

**근거**: 글로벌 클라이언트(일본·중국·영미·유럽)에 KST로 변환된 시각을 내려주는 것은 의미가 없다 — 각 클라이언트는 자기 로컬로 다시 변환해야 하므로, 서버가 중간에 KST로 한 번 바꾸는 건 불필요한 변환 단계이자 실수 유발 지점이다. UTC를 표준 계약으로 고정하고, 로컬 표시는 전적으로 클라이언트 책임으로 넘긴다.

**트레이드오프**: 프론트엔드가 지금까지 "서버가 KST로 준다"고 암묵적으로 가정한 코드가 있다면 깨진다 — 프론트엔드 팀과 계약 변경을 사전 공지해야 한다. (§6 미결정 사항 참고)

### 3.3 `Member`에 `timezone`/`countryCode` 필드 추가

**결정**: `Member` 도메인에 다음 필드 추가.

```java
private String timezone;     // IANA tz ID, 예: "Asia/Tokyo", "America/New_York" (가입 시 필수, §3.3.1)
private String countryCode;  // ISO 3166-1 alpha-2, 예: "JP", "CN", "US", "GB", "DE"
```

**수집 방식 (확정)**: IP 기반 지오로케이션으로 추정하지 않는다. 여행 중이거나 VPN을 쓰는 회원의 "거주 시간대"를 IP로 잘못 추정하면 향후 로컬 기준 로직이 어긋난다. 대신:
- 가입 시 클라이언트가 `Intl.DateTimeFormat().resolvedOptions().timeZone`(웹) 또는 `TimeZone.getDefault()`(모바일)로 자동 감지한 값을 **별도 확인 화면 없이 즉시 저장**한다.
- 회원 설정에서 언제든 수동 변경 가능(설정 화면은 필요 — "즉시 저장"은 가입 시점 UX에 한정된 결정).

**활용처**: "이번 주"/"오늘" 같은 상대적 날짜 표현이 필요한 기능(현재는 없으나 recruit/community 모듈에서 발생 가능), 통계·리포트의 리전별 세그먼트, 향후 마감일 계산(§3.5)의 기준. **알림(푸시/이메일) 발송 시각을 회원 로컬 기준으로 제어하는 기능은 현재 스코프가 아니다** — 애초에 푸시/이메일 발송 인프라 자체가 코드에 없으므로 지금 설계하지 않는다. 다만 필드 자체는 다른 용도로도 필요하므로 지금 추가해둔다.

**트레이드오프**: 애초 설계는 미설정 회원(가입 UX를 거치지 않은 레거시 데이터)이 `timezone == null` 상태가 될 수 있다고 가정했으나, 구현 시 §3.3.1에서 더 단순한 방향(가입 시 필수값 강제)으로 확정했다. 라이트 마이그레이션 회원은 §3.3.2에서 별도 확정.

#### 3.3.1 미설정 시 폴백 정책 (구현 반영: 가입 시 필수값으로 확정, 폴백 불필요)

**결정(구현 완료, 최초 설계에서 정정)**: `timezone`은 `Member.validateTimezone()`이 가입 경로(자체 가입·소셜 가입 공통)에서 null·유효하지 않은 IANA ID를 예외로 거부하므로, 신규 가입 회원은 항상 값이 존재한다. 최초 설계안이었던 "null이면 UTC로 폴백"은 채택하지 않았다 — null 상태 자체가 발생하지 않도록 가입 단계에서 막는 편이 "표시 로직마다 null 체크+폴백을 반복하는" 것보다 단순하고 누락 위험이 적다. 프로필 수정(`UpdateInfoCommand`)에서는 `timezone`이 null이면 "값을 바꾸지 않음"으로 해석해 기존 값을 유지하므로, 저장된 값이 사후에 null로 바뀌는 경로도 없다.

**근거**: KST를 기본값으로 암묵 대입하지 않는다는 원래 방침(글로벌화 이후 "한국 서비스니까 기본은 KST" 가정 폐기)은 그대로 유효하다 — 다만 그 방침을 "null일 때 UTC로 폴백"이 아니라 "애초에 null을 허용하지 않음"으로 구현했다는 점이 최초 설계안과 다르다. 라이트 마이그레이션 회원(§3.3.2)은 이 가입 플로우를 거치지 않으므로 마이그레이션 배치가 별도로 `Asia/Seoul`을 명시 대입해야 하는 점은 동일하다.

#### 3.3.2 라이트(Laiteu) 마이그레이션 회원의 timezone (확정)

**결정**: 마이그레이션 배치에서 기존 라이트 회원 전원에게 `timezone = "Asia/Seoul"`을 명시 대입한다. §3.3.1의 일반 폴백(UTC)과 별개의 예외 처리다.

**근거**: 라이트는 한국 서비스였으므로 마이그레이션 대상 회원은 사실상 전원 한국 거주자로 간주할 수 있다 — 이 경우는 "지역을 모른다"가 아니라 "지역을 안다"에 해당하므로, 안전한 기본값(UTC)보다 실제로 맞는 값(KST)을 넣는 것이 낫다. 이후 회원이 설정에서 직접 변경 가능.

### 3.4 로깅 타임스탬프 UTC 고정

**결정**: `logback-spring.xml`을 신설(또는 `application.yml`의 `logging.pattern`)해 타임스탬프를 UTC로 명시. 3.1의 컨테이너 `TZ=UTC`가 적용되면 자동으로 해결되지만, 로그 자체에 시간대 표기(`Z` 또는 `UTC` 라벨)를 남겨 관측 도구(Datadog/CloudWatch 등)에서 오인하지 않도록 한다.

**근거**: 다국적 사용자를 상대하는 백엔드의 로그는 "어느 리전 개발자가 보든" 동일 기준이어야 한다. 리전별로 로그 시간대가 다르면 장애 시각 상관관계 분석이 어긋난다. 이는 사용자에게 보여주는 시간(로컬 변환)과는 별개의 관심사다.

**트레이드오프**: 없음 — 순수 관측성 개선.

### 3.5 향후 마감일·일정 필드(recruit 등 신규 모듈) 설계 원칙

현재 recruit/community 모듈은 미구현이지만([[project_community_module]] 참고), 구인 마감일처럼 "특정 시각까지"라는 의미를 가진 필드가 곧 추가될 것이 예상되므로 원칙을 미리 못박아둔다.

**결정**:
- 마감일/시작일 등 절대 시각을 의미하는 필드는 **`Instant`로만 저장**한다.
- 사용자가 "2026년 8월 1일 마감"처럼 날짜만 입력하면, **입력한 회원의 `timezone` 기준 자정(또는 명시된 시각)을 서버가 즉시 `Instant`로 환산해 저장**한다. 저장 이후에는 순수 UTC 인스턴트만 남고, 원본 시간대 정보에 의존하지 않는다.
- "마감까지 N일 남음" 같은 표시는 각 조회자의 `timezone` 기준으로 매번 재계산한다 — 저장 시점 계산 값을 캐싱하지 않는다(작성자와 조회자의 시간대가 다르면 D-day 표시가 달라질 수 있다는 점을 UX적으로 인지해야 함, §6).

**근거**: 마감일은 이 프로젝트에서 가장 시간대 버그가 나기 쉬운 지점이다 — "author 기준"과 "server 기준"과 "viewer 기준"이 섞이면 마감이 지난 공고가 계속 보이거나, 아직 안 지났는데 마감 처리되는 사고가 난다. 저장은 단일 기준(UTC), 계산 시점의 기준(누구의 시간대인지)을 코드 레벨에서 항상 명시하는 규칙을 지금 세워두면 향후 모듈 구현 시 반복 논의를 줄인다.

### 3.6 기존 "KST 고정" 메모리 정책 개정

**결정**: [[feedback_timezone]] 메모의 "이 프로젝트의 모든 시간은 KST로 처리" 규칙을 "저장·연산은 UTC(Instant), 표시는 회원의 timezone 기준 로컬"로 갱신한다. 이 설계가 승인되면 해당 메모리 파일을 함께 수정한다(현재는 설계 단계라 보류).

**근거**: 글로벌 서비스 전환의 전제 자체가 기존 KST 고정 정책과 모순되므로, 설계 승인 시점에 정책 문서/메모리를 반드시 함께 갱신해야 실제 구현 단계에서 다시 KST 하드코딩이 재발하지 않는다.

## 4. 리전별 참고 (일본·중국·영미·유럽)

| 리전 | IANA 대표 tz | DST 여부 | 비고 |
|------|-------------|---------|------|
| 일본 | `Asia/Tokyo` | 없음 (UTC+9 고정) | 한국(UTC+9)과 오프셋 동일 — 헷갈리기 쉽지만 IANA ID로 저장하면 문제없음 |
| 중국 | `Asia/Shanghai` | 없음 (UTC+8 고정, 전역 단일 시간대) | 신장 등 지리적으론 여러 시간대지만 공식적으로 전역 단일 시간대 사용 |
| 영국 | `Europe/London` | 있음 (BST) | UTC+0(겨울)/UTC+1(여름) |
| 미국 | `America/New_York`, `America/Los_Angeles` 등 | 있음 | 대륙 국가라 **국가 코드만으로는 시간대를 못 정한다** — 반드시 도시 단위 IANA ID 필요 |
| 유럽(주요국) | `Europe/Paris`, `Europe/Berlin` 등 | 있음 (CEST) | UTC+1(겨울)/UTC+2(여름) |

**시사점**: 미국·유럽은 DST가 있고, 일본·중국은 없다 — 오프셋 고정 저장이 절대 안 되는 이유가 바로 이것이다(§2-2). 또한 미국처럼 국가 하나에 여러 시간대가 있는 리전은 `countryCode`만으로 시간대를 유추할 수 없으므로 `timezone` 필드가 `countryCode`와 별개로 반드시 필요하다.

## 5. 시간대와 맞물리지만 이 문서 범위 밖인 것 (플래그만)

사용자가 "일본·중국·영미·유럽 시간대 관리"를 물었지만, 실제로 이 리전들을 서비스하려면 시간대 외에도 아래가 함께 걸린다. 각각 별도 설계가 필요하므로 여기서는 존재만 표시한다.

### 5.1 i18n (메시지 다국어화)
현재 `GlobalExceptionHandler`, 검증 메시지, `ActiveRegion` 등 enum 주석까지 전부 하드코딩된 한국어다. `MessageSource`/`Accept-Language` 기반 로케일 처리가 전무하다. 시간대 작업과 별개의 큰 과제.

### 5.2 `ActiveRegion` enum의 글로벌화
현재 서울·경기·대전·대구·광주·부산 등 한국 행정구역 전용이다. 글로벌 회원의 "활동 지역"을 표현하려면 국가(`countryCode`) + 지역의 계층 구조로 재설계가 필요하다.

### 5.3 중국(CN) 스코프 — 해외 거주 중국어 사용자 대상으로 확정

**결정**: 중국은 "중국 본토 정식 서비스"가 아니라 **해외 거주 중국어 사용자 대상**으로 스코프를 확정한다. 이 결정으로 아래 우려가 대부분 해소된다.

**이메일 자체 로그인 — 중국 본토 접속 가능 여부 (참고용, 필수 대응 아님)**
- 코드 확인 결과 `AuthServiceImpl.loginWithEmail`/`registerWithEmail`은 `FirebaseVerifier`를 호출하지 않는다 — 이메일 로그인(BCrypt 검증)은 Firebase/Google 의존이 전혀 없다(Google 로그인 메서드만 `firebaseVerifier.verify()` 호출). 즉 이메일 로그인 자체는 GFW의 "서비스 단위 차단"(Google·Firebase·Facebook 등 도메인 차단) 대상이 아니다.
- 다만 GFW는 서비스 화이트리스트가 아니라 IP 대역·TLS SNI 단위의 DPI(딥패킷인스펙션)/차단/스로틀링을 하므로, 백엔드가 AWS/GCP 등 해외 IP에 있으면 로그인 방식과 무관하게 접속 자체가 불안정할 수 있다.
- **해외 거주 사용자는 애초에 중국 본토 네트워크로 접속하지 않으므로 이 문제 자체가 발생하지 않는다.** 일시 귀국 등으로 중국 본토에서 접속하는 소수 케이스가 불안정을 겪을 수 있으나, 이는 서비스 대상 스코프 밖이므로 별도 대응하지 않는다.

**DB(MongoDB Atlas) 접근성 — 해당 없음**
- 클라이언트가 DB에 직접 접속하는 구조가 아니라 백엔드 서버만 MongoDB Atlas에 접속한다. 백엔드가 중국 본토 밖에 호스팅되어 있으면(현재도 그렇고, 앞으로도 그럴 것) DB 접근성 문제는 애초에 성립하지 않는다 — 클라이언트-백엔드 구간의 네트워크 경로만 문제가 될 수 있는데, 위 항목과 동일한 이유로 해외 거주 스코프에서는 무관하다.

**남는 것은 시간대(`Asia/Shanghai`)와 i18n(중국어) 뿐** — WeChat 로그인, ICP 라이선스, 중국 전용 CDN/인프라는 이 스코프에서 불필요하다.

**트레이드오프**: 향후 중국 본토 정식 서비스로 스코프가 확장되면 이 결정 전체를 재검토해야 한다(WeChat 로그인, ICP 라이선스, 중국 리전 인프라 등이 다시 필요해짐). 지금은 해외 거주 스코프로 명확히 한정한다.

### 5.4 지역별 법적 요구사항 (특히 유럽 GDPR)
- 유럽(GDPR): 데이터 보관 위치(residency), 삭제권(Right to Erasure) — 현재 `Member.deactivate()`가 soft delete + 개인정보 클리어(`loginEmail`, `handle`, `passwordHash` null 처리)를 하고 있어 출발점은 있으나 GDPR 기준 완전 삭제(hard delete) 요건까지 검토 필요.
- `TermsAgreement`가 이미 항목별(`privacyPolicy`, `serviceTerms`, `thirdPartyProvision`) 동의를 분리 저장하는 구조라 GDPR의 세분화된 동의(granular consent) 요건과 방향은 맞음 — 리전별 필수/선택 약관 항목이 달라질 수 있다는 점만 추가 검토.

### 5.5 날짜·숫자 로케일 포맷
`MM/DD/YYYY`(미국) vs `DD.MM.YYYY`(유럽) vs `YYYY年MM月DD日`(일본·중국) 같은 표시 포맷은 §2-4 원칙대로 서버가 UTC 인스턴트만 내려주면 클라이언트 로케일 렌더링으로 해결된다 — 서버가 별도 작업할 필요는 없지만, 프론트엔드 가이드에 "서버가 포맷된 문자열을 주지 않는다"는 계약을 명시해야 한다.
